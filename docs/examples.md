# Примеры использования

Сценарии, где связка **AI-агент + Checko MCP** показывает себя сильнее всего: многошаговые обходы графа сущностей, batch-обработка с интерпретацией, склейка данных из разных источников в связный аналитический вывод.

Общий принцип: ручной просмотр справочных карточек даёт сырые факты и флаги. Агент же обходит граф из десятков сущностей, склеивает данные из разных эндпоинтов API и формулирует **вывод** — не таблицу фактов, а аргументированное заключение.

> [!IMPORTANT]
> Основной фокус примеров — анализ юридических лиц и ИП (публичные сведения ЕГРЮЛ/ЕГРИП). Сценарии массового анализа физических лиц намеренно исключены — это потенциальное нарушение [152-ФЗ](../LEGAL.md). Сценарий #3 обращается к данным конкретного директора через `get_person`: это допустимо, поскольку руководитель раскрыт в ЕГРЮЛ публично и проверка ведётся в рамках конкретной деловой задачи. Полный аудит физлица — только через отдельный prompt `audit_person` при наличии законного основания.

> [!WARNING]
> Финальные выводы делает AI-модель, а она может ошибаться: путать поля, додумывать факты, неверно интерпретировать суммы. Перед существенными решениями перепроверяйте ключевые цифры в первоисточниках (ЕГРЮЛ ФНС, КАД.Арбитр, ЕФРСБ, ГИР БО).

## 1. «Распутай схему» — граф связанных юрлиц с интерпретацией

**Когда нужно.** Перед сделкой M&A, при подозрении на дробление бизнеса, при расследовании происхождения активов или при анализе группы компаний под общим бенефициаром.

**Почему это сложно вручную.** Связи первого уровня посмотреть несложно, но обход 2–3 уровней вглубь и вывод о паттерне («дробление под УСН», «синхронная ликвидация», «вывод активов») требуют десятков ручных переходов и собственной аналитики поверх сырых данных.

**Пример запроса:**

> «Вот ИНН компании `<ИНН>`. Найди всю группу компаний под общим бенефициаром: пройди по учредителям 2–3 уровня вглубь, посмотри какие из связанных юрлиц действующие, какие ликвидированы, есть ли синхронные ликвидации или признаки дробления бизнеса.»

**Pipeline (агент строит сам):**

1. `get_company(inn=...)` — стартовая компания. Сразу забираем массив `СвязУчред[]` (v2.4): связанные через общих учредителей компании — API возвращает их агрегированно, без необходимости отдельно вызывать `get_person`.
2. По каждому учредителю-юрлицу и каждой записи из `СвязУчред[]` → `get_company(ogrn=...)`.
3. Повторить шаг 2 для следующего уровня вложенности (учредители учредителей) — обычно хватает 2 уровней.
4. `get_timeline(ogrn=...)` по подозрительным узлам — проверка синхронности дат регистрации, смены адреса, ликвидации.

Итого: **20–40 вызовов API**, ~30–60 секунд работы агента. Без обращения к `get_person` — весь обход на публичных сведениях ЕГРЮЛ по юрлицам.

**Что получит пользователь:**

- Карта группы (компания → учредители → дочки → внучки).
- Список ликвидированных юрлиц с датами — выявление «волн» ликвидаций.
- Совпадающие адреса, ОКВЭДы, общие контактные данные.
- Гипотеза о паттерне: дробление бизнеса, защита активов, технические юрлица.

**На что обратить внимание.** Глубина обхода = квота. Если у группы реально 50+ юрлиц, ограничьте обход вторым уровнем или попросите агент сначала составить список ОГРН и подтвердить, прежде чем тянуть полные карточки.

## 2. Массовая фильтрация контрагентов по сложному критерию

**Когда нужно.** Финансовый контроль дебиторов, мониторинг базы поставщиков, due diligence портфеля закупок, ежеквартальная ревизия рисков.

**Почему это сложно вручную.** Готовые системы мониторинга обычно поддерживают триггеры по одному простому критерию; составной фильтр вида «(новые иски от ФНС > X) ИЛИ (смена директора) ИЛИ (свежее намерение о банкротстве)» под конкретный кейс настроить нельзя — а проходить 80 карточек руками никто не будет.

**Пример запроса:**

> «Вот список из 80 ИНН наших поставщиков (далее CSV или просто перечисление). Оцени риск банкротства каждого и верни только тех, у кого за последние 90 дней появились иски от ФНС суммой больше 1 млн ₽, ИЛИ сменился директор, ИЛИ в Федресурсе есть сообщения CreditorIntentionGoToCourt. По каждому проблемному — две строки обоснования.»

**Pipeline:**

1. Для каждого ИНН: `get_company(inn=...)` + `get_legal_cases(inn=..., role="defendant", actual=true, active=true)` + `get_fedresurs(inn=...)` + `get_timeline(inn=...)`.
2. Составной фильтр (AND/OR по разным источникам) применяется на стороне LLM — Checko API таких фильтров не поддерживает, поэтому без агента это руками не свернуть.
3. Возвращаются только релевантные ИНН с конкретикой.

Итого: **3–5 вызовов на ИНН**, для 80 контрагентов — порядка 300–400 запросов. Имеет смысл сначала проверить квоту через `meta.balance` и при необходимости разбить на батчи.

**Что получит пользователь:**

- Короткий список (5–15 проблемных из 80).
- По каждому — конкретное обоснование с цифрами и датами.
- Приоритизация (🔴 / 🟠 / 🟡).

**На что обратить внимание.**

- Перед запуском batch попросите агент **оценить стоимость** (количество ИНН × средняя цена за вызов) и подтвердить.
- Для регулярного мониторинга это разовый прогон; постоянный мониторинг лучше делать отдельным cron-скриптом, не через интерактивного агента.

## 3. Анализ номинальности директора через его портфель

**Когда нужно.** Перед заключением договора с малознакомой компанией, при подозрении на технического контрагента, в рамках комплаенс-проверки.

**Почему это сложно вручную.** Сам по себе флаг `массовый руководитель: да` ни о чём не говорит — нужно открыть портфель компаний и сделать вывод, **серийный это предприниматель или номинальный директор**. Разница принципиальна: один реально ведёт 47 бизнесов, другой числится в 47 технических юрлицах с нулевой деятельностью. Ручной анализ — час работы.

**Пример запроса:**

> «У компании ИНН `<ИНН>` у директора стоит флаг "массовый руководитель". Объясни — это реально номинальное лицо или серийный предприниматель? Посмотри его портфель компаний.»

**Pipeline:**

1. `get_company(inn=...)` — берём ФИО и ИНН директора из `Руковод[]`.
2. `get_person(inn=<ИНН директора>)` — список всех его компаний и ИП.
3. По выборке компаний (10–15 наиболее значимых) → `get_company(ogrn=...)` + `get_finances(ogrn=..., extended=true)`.
4. Агент строит распределение: сколько действующих, сколько ликвидированных, сколько с реальной выручкой, сколько с нулевой, сколько в банкротстве.

**Что получит пользователь:**

Вывод одного из двух типов:

- **Серийный предприниматель:** *«Из 47 компаний 30 действующих с выручкой от 5 до 200 млн ₽, разные ОКВЭДы, разные регионы. Это активный бизнесмен, флаг "массовый" формальный.»*
- **Номинал / технические юрлица:** *«Из 47 компаний 31 ликвидирована за 2 года, у 9 нулевая выручка, у 5 — открыты процедуры банкротства, действующих с реальной деятельностью — 2. Признаки массового номинального директора.»*

**На что обратить внимание.** Запрос `get_person` обращается к персональным данным физлица (ФИО, связи). В контексте проверки контрагента это допустимо (директор раскрыт в ЕГРЮЛ публично), но не злоупотребляйте — не используйте для сбора профилей частных лиц.

## 4. Историческая реконструкция бизнеса как нарратив

**Когда нужно.** Понять траекторию компании перед сделкой, объяснить акционеру/инвестору что произошло за период, подготовить аналитическую справку, восстановить причинно-следственные связи.

**Почему это сложно вручную.** Сырые факты лежат в разных разделах: даты — в timeline, суммы — в финансах, иски — отдельно, публикации Федресурса — ещё отдельно. Собрать **связный нарратив** и склеить события (смена директора + падение выручки + появление налоговых исков = одна история) — отдельная аналитическая работа.

**Пример запроса:**

> «Расскажи как нарратив: что происходило с компанией ОГРН `<ОГРН>` за последние 3 года. Меня интересует траектория — почему сейчас она в текущем состоянии, что было поворотными точками.»

**Pipeline:**

1. `get_timeline(ogrn=...)` — все изменения регистрационных данных по датам.
2. `get_finances(ogrn=..., extended=true)` — динамика выручки/прибыли/капитала за 5 лет.
3. `get_legal_cases(ogrn=..., actual=true)` — иски с датами и суммами.
4. `get_fedresurs(ogrn=...)` — публикации Федресурса по датам.
5. `get_contracts(ogrn=..., law=44)` + `get_contracts(ogrn=..., law=223)` — динамика выручки от госконтрактов.
6. Агент строит общую timeline и формирует причинно-следственный текст.

**Что получит пользователь:**

Связный нарратив вида:

> *«В Q1-2023 из учредителей вышел мажоритарий (доля 60%), сменился ОКВЭД с производства на оптовую торговлю. В 2024 выручка упала с 480 до 110 млн ₽ (-77%), госконтракты прекратились, появились первые иски от ФНС на 12 млн ₽. В Q3-2025 — два сообщения CreditorIntentionGoToCourt от поставщиков. Траектория: поворотная точка — выход мажоритария и смена профиля; далее — постепенный отказ от деятельности, сейчас компания в зоне предбанкротства.»*

**На что обратить внимание.** Это самый «текстовый» сценарий — здесь риск галлюцинаций выше среднего. Агент может перепутать года, неверно сопоставить событие и причину. **Обязательно перепроверяйте ключевые даты и суммы** в первоисточнике, особенно если выводы используются в документах для третьих лиц.

## Чего нет в этих примерах и почему

- **Массовая проверка физлиц по списку ИНН.** Потенциальное нарушение 152-ФЗ — обработка персональных данных без законного основания. См. [`LEGAL.md`](../LEGAL.md).
- **Поиск «бизнес-партнёров» через пересечения учредителей-физлиц.** Технически возможен, но превращает агрегатор публичных данных в инструмент построения профилей частных лиц — выходит за рамки целей публикации сведений в ЕГРЮЛ.
- **Скоринг физлиц на основании косвенных признаков.** Не входит в задачи проекта; для финансовых решений по физлицам предусмотрены отдельные регулируемые процедуры.

Если вам нужен аудит **конкретного** физлица с законным основанием (например, проверка контрагента-ИП по запросу клиента или собственная проверка), используйте prompt `audit_person` — он встроенно требует подтверждения основания.
